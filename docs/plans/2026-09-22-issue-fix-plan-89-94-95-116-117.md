## 1. #116 Oracle 引号混合大小写标识符被折叠（bug）

### 根因（已核实）

标识符折叠方向反了。**目录返回的物理名是权威大小写**，但渲染/探针路径对它再做一次
「未加引号名 → 大写」折叠：

- `backend/mod.rs:495 quote_ident_scheme`：`scheme == "oracle"` → `to_ascii_uppercase()`
- `backend/oracle/dialect.rs:495` 与 `backend/oracle_native/dialect.rs:494` 的 `oracle_ident`：同样折叠
- 消费方全部中招：`delta_diff/bucket_diff.rs:171 probe_side`、`delta_diff/hash_diff.rs:630 key_range`、
  Oracle 渲染器 `normalize_expr`（`oracle_ident(&col.name)`，两个后端各一处）、
  `render_checksum_sql` / `render_batch_checksum_sql` / keyset 的 `oracle_ident(key)`
- `MIN("MYKEY")` → ORA-00904 → rust 驱动关连接且无错误包 → 后续语句一律
  `connection closed`，真实原因被埋掉

关键事实（`delta_diff/metadata.rs:187 build_table_plan`）：**列名与键名进 spec 前已全部
解析为目录物理名**（目录直读，或 `--key`/`--columns` 经 `find_unique_ci` 归一到 `col.name`）。
`schema` 与 `table` 仍是用户输入。因此「目录名 vs 用户名」在渲染层是可判定的。

### 设计

1. **trait 扩展**：`Dialect` 新增 `quote_catalog_ident(&self, name) -> String`，
   默认实现 = `quote_ident(name)`（MySQL/GaussDB/DuckDB 行为不变）。
   Oracle 两个后端覆写为**原样引用**（`quote_ident('"', name)`，不折叠）。
   语义：`quote_ident` = 用户输入（保留折叠），`quote_catalog_ident` = 目录名（原样）。
2. **调用点改造**（仅改传目录名的位置）：
   - `normalize_expr`：`oracle_ident(&col.name)` → `quote_catalog_ident`（两个后端）
   - `render_checksum_sql` / `render_batch_checksum_sql` / keyset 渲染里的 key：
     spec 的 key/columns 已目录解析 → `quote_catalog_ident`
   - `bucket_diff.rs::probe_side`、`hash_diff.rs::key_range`：`dialect.quote_ident` → `quote_catalog_ident`
   - `backend/mod.rs:650 key_sort_expr`：核对调用方传入名字的来源后同样切换
   - `quoted_table`（schema/table）：保持 `oracle_ident` 折叠（用户输入）
3. **错误可诊断**：Oracle conn 查询层识别 `closed the connection without an error packet`，
   追加提示「可能是不存在的列/标识符大小写不匹配（如引号混合大小写标识符）」。
4. **范围外顺带核对**：`synth/export.rs:138 export_ident` 对 oracle 也折叠目录列名，
   同类隐患；本 issue 只改 delta-diff 路径，导出路径单独开 issue 记录。

## 2. #94 derive 条件函数 `if()` + 布尔目标列

### 现状（已核实）

- `synth/expr.rs` 文法冻结（§2.2）；解析器对函数调用报 `Disallowed { construct: "function call" }`；
  词法器已有 `Ident`/`LParen`/`Comma`/`Dot` token，无需新增标点。
- `eval_decimal`（expr.rs:878）遇 Bool 报 `TypeMismatch { op: "decimal result" }`，即 issue 复现路径。
- `DeriveStep`（generator.rs:1723）只有 `is_integer`/`scale` 两个输出形态开关；
  `LogicalType`（model.rs:102）只有 `Numerical/Categorical/Datetime`，无布尔。
- `branches[].predicate` 走 `eval_bool`，本设计不触碰。

### 设计

1. **函数白名单机制**：AST 加 `Node::Call { name: String, args: Vec<Node> }`；
   解析时按白名单表校验函数名与参数个数（fail-fast，报错沿用
   ``function `xxx` is not permitted...`` 风格，未知名给出已知函数列表）。
   首批函数：`if(cond, then, else)`。`if` 语义：
   - `cond` 必须求值为 Bool（否则 `NonBooleanPredicate`）
   - `then`/`else` 静态类型须一致（number 或 string）
   - **惰性求值**：只求值被选分支（未选分支中的除零不触发），文档明示
2. **静态结果类型推断**（expr.rs 纯函数 `infer_type(&Node) -> Ty`，Ty ∈ Number/String/Bool）：
   - 加载期可用：derive 表达式若推断为 Bool 而以 `eval_decimal` 求值 → 更清晰的
     专用错误（保留旧 TypeMismatch 兜底）
3. **布尔目标列**：derive 求值按「表达式推断类型」分流——Bool → `eval_bool` 输出
   `Value::Bool`；Number/String → 现有路径。目标列兼容性检查放 `DerivePlan::build`
   （有 model）：目标列训练值为 bool（JSON bool 或 categorical 全 true/false 水平）
   而表达式非 Bool → 明确报错；反之数值列配 Bool 表达式同样报错。
   不新增 `LogicalType::Boolean`（避免动 profile/marginal 全链路，scope 收敛）。
4. **文档**：UserGuide §10.5 已知限制 #6 撤销，补白名单与 `if` 语义说明。

### TDD 循环

|---|---|---|
| R1 | `should_evaluate_if_with_boolean_condition`（`if(active == 1 && store_id > 0, 1, 0)` → 1/0 两分支） | `expr.rs` |
| R2 | `should_lazy_evaluate_untaken_branch`（`if(x == 0, 1, 10 / x)`，x=0 时报错、x≠0 时正常） | `expr.rs` |
| R3 | `should_reject_if_with_non_boolean_condition` / `should_reject_if_branch_type_conflict` | `expr.rs` |
| R4 | `should_reject_unknown_function_with_known_list` | `expr.rs` |
| R5 | `should_infer_expression_result_type`（比较/逻辑→Bool，算术→Number，concat→String） | `expr.rs` |
| R6 | generator：`derive: expr: "active == 1 && store_id > 0"` 目标列为 bool 训练值 → 生成值全为 `true/false`；数值列配 Bool 表达式 → 计划期报错 | `generator.rs` |
| R7 | 回归：既有 derive/branch 全部测试不变全绿 | 全仓 |

issue 复现 YAML `derive: expr: "if(active == 1 && store_id > 0, 1, 0)"` 合法且生成值正确；
`branches[].predicate` 行为零变化。

## 3. #95 PII phone 按训练值地域生成

### 现状（已核实）

- `pii.rs:309` phone 模板固定 `+1-{03}-{03}-{04}`。
- `anonymize_model_column`（pii.rs:98）刻意清空全部格式元数据 → 「按训练值地域」必须走
  **新的、不可逆的样式提示**，不能复用被清掉的字段。
- `looks_like_phone`（pii.rs:253）内容投票要求带 `+` 或分隔符：裸 11 位 `138...` 值
  **不会**触发内容投票，识别靠列名（phone/mobile/tel）。样式推断只对已判 PII 的列做。
- `matches_format` 接受 7–15 位数字 + `+ - space ( )`：`+86-138-XXXX-XXXX` 天然合法。
- warning 通道：`eprintln!("warning: ...")`（cmd.rs 惯例），generator 单次运行内去重。

### 设计

1. **样式枚举** `PhoneStyle`（pii.rs）：`UsDefault`（回退）/ `CnMobile { prefix: [u8; 3] }`。
2. **训练期推断**：对已判 `pii: phone` 的列，采样值归一化（剥 `+86`/`86` 前缀与分隔符）后，
   ≥80% 匹配 `1[3-9]\d{9}` → `CnMobile { prefix }`（prefix 取训练值号段众数）；
   无法识别 → `UsDefault` + 生成期一次性 warning。
3. **模型存储**：`ColumnModel` 加 `#[serde(default, skip_serializing_if = "Option::is_none")]
   pii_phone_style: Option<PhoneStyle>`——additive，旧模型缺字段 = 默认，
   **`model version: 1` 不变**（符合 #89 兼容要求）。只存样式与 3 位号段，不存原值
   （号段保留是 issue 明示的泄漏权衡）。
4. **生成期**：`generate_value` 按 style 出号：CnMobile → `1{prefix}{8 位随机}`（渲染带
   `+86-` 前缀，与 issue 期望格式一致）；随机部分保证不等于任何训练值尾部结构
   （假号化语义；与 `pii_unique`/`pii_stable_mapping` 正交，走 PiiPlan 现有机制）。

## 4. #117 跨表派生键（derive 沿 relationship 引父表行级值）

### 现状（已核实）

- `DeriveRule`（rules.rs:222）expr 仅同表；`validate_derive_rules`（rules.rs:619）只认本表列。
- `RelPool`（generator.rs:92）只包 `FkPool`（值池 + 权重，无父行级对应）。
- 父表在表级拓扑序先于子表完成生成（含 derive/branch 全阶段）→ 父行快照可得。
- **`||` 冲突**：现文法 `||` 是逻辑 OR（predicate 在用），issue 例子用 `||` 做 concat。
  **裁决：`||` 保持 OR；拼接用 `concat(a, b)` 函数**（落在 #94 白名单机制上），文档明示。
- Branch repair 可翻列「never FK, referenced, derived or pinned」（generator.rs:598 注释），
  但 repair.set 可改 derive 表达式读的本地列 → 现有 `linked_derive_recompute` 机制需兼容
  跨表步骤。

### 设计

1. **文法**：primary 扩展 `parent.<col>` 限定引用（lexer 已有 `Dot`；解析器现把属性访问报
   Disallowed，改为仅放行 `parent.` 前缀，其余照旧拒绝）。
   `referenced_columns` 返回带限定名 `parent.<col>`（本地列名不含 `.`，天然无歧义）。
   函数复用 #94 白名单：`concat`、`substr(s, start[, len])`、`right(s, n)`、`left(s, n)`。
2. **配置**：`Relationship`（rules.rs:269）加 `#[serde(default)] derive: Vec<DeriveRule>`。
   子表某列 = `parent.<col>` 与本地列的函数。
3. **生成期**：
   - `build_rel_pools`：当 relationship 带 derive 时，捕获父表（已生成完毕的 rows）
     `父键 → 被引用列值快照`（只捕获被引用列，控内存）。
   - `DerivePlan` 扩展：跨表步骤的 lookup 对 `parent.<col>` 查快照（按该 relationship 的
     FK 列当前行值索引）；本地步骤不变；**同一 Kahn 拓扑合并本地与跨表步骤**
     （跨表依赖视为已就绪）。求值位置仍在 phase 5（FK 已分配、本地值已就绪）。
   - FK 为 NULL（null_rate）→ `parent.<col>` 取 NULL → NULL 传播（与现有语义一致）。
   - branch repair 的 `linked_derive_recompute` 复用同一 merged plan（含跨表步骤）。
4. **校验**（rules.rs `validate_derive_rules` 扩展 + 生成期复核）：
   - 目标列不得是 relationship pk（FK 列）/ fixed/values/fixed_range / 被别的表引用的父键
     （现有检查模式复用）
   - `parent.<col>` 必须存在于被引用父表模型列；relationship 缺对应 FK 时报错
   - 循环检测沿用 Kahn（跨表引用视为已就绪边）；禁止子表 relationship-derive 引用
     「未在本 relationship 声明的父表」
5. **求值顺序明示**：FK 分配（phase 3）→ 本地覆盖（phase 4）→ merged derive（phase 5，
   本地 + 跨表一个拓扑序）→ branch repair（可 set 覆盖，`linked_derive_recompute` 重算
   merged plan）。

## 附：`||` 与 concat 的跨库实测（2026-09-22，本机容器实测）

| 表达式 | MySQL 8 | Oracle 23ai | openGauss 5.0 | DuckDB |
|---|---|---|---|---|
| `'a' || 'b'` | `0`（逻辑 OR） | `ab`（拼接） | `ab`（拼接） | `ab`（拼接） |
| `CONCAT('a','b')` | `ab` | `ab`（仅两参） | `ab` | `ab` |
| `CONCAT(a,b,c)` | `abc` | 不支持（需嵌套） | `abc` | `abc` |

结论：`||` 语义在四个后端**不一致**（MySQL 默认 = 逻辑 OR），「跟随数据库」无统一定义。
synth 表达式在 Rust 侧求值、从不下推 SQL，故维持既有冻结文法 `||` = 逻辑 OR
（与 MySQL 语义一致，且向后兼容 branch predicate）；拼接统一用 `concat()`（#94/#117
白名单函数，Rust 侧 n 元实现，不受 Oracle SQL 层两参限制）。
